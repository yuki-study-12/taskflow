# TaskFlow 機能仕様書

## 1. 概要

TaskFlow は、チーム向けのプロジェクト・タスク管理アプリケーションである。プロジェクト単位でカンバンボードを持ち、メンバーがタスクの作成・担当者アサイン・進捗管理・コメントによるコミュニケーションを行う。ドラッグ&ドロップによるタスク移動と、SignalRによるリアルタイム同期・通知を備える。

## 2. システム構成（アーキテクチャ）

Clean Architecture 構成の .NET 10 ソリューション。

| プロジェクト | 役割 |
|---|---|
| `TaskFlow.Domain` | ドメインエンティティ・値オブジェクト・ドメインイベント |
| `TaskFlow.Application` | ユースケース（Command/Query）、バリデーション、通知イベントハンドラ |
| `TaskFlow.Infrastructure` | EF Core永続化、認証（JWT）、外部連携（Claude API、SMTP） |
| `TaskFlow.Contracts` | WebAPIのリクエスト/レスポンスDTO |
| `TaskFlow.WebAPI` | ASP.NET Core Minimal API、SignalR Hub、認証・例外ハンドリング |
| `TaskFlow.Web` | Blazor Server フロントエンド |

依存の方向は `WebAPI/Web → Infrastructure → Application → Domain` であり、Domain層は他層に依存しない。

## 3. ドメインモデル

### 3.1 Project（プロジェクト）

| フィールド | 型 | 説明 |
|---|---|---|
| `Id` | Guid | 主キー |
| `Name` | string | プロジェクト名（必須、200文字以内） |
| `Description` | string | 説明（必須、1000文字以内） |
| `Members` | ProjectMember[] | 参加メンバー一覧 |

- `Project.Create(name, description, ownerId)`: 作成者を自動的に `Owner` として追加し、`ProjectCreatedEvent` を発行する。
- `AddMember(userId, role)`: role に `Owner` は指定不可。既存メンバーの追加はエラー。`MemberInvitedEvent` を発行。
- `UpdateMemberRole(userId, newRole)`: `Owner` への変更、および Owner自身のロール変更は不可。
- `RemoveMember(userId)`: Owner は削除不可。

### 3.2 ProjectMember / MemberRole

`MemberRole` は以下の3値のみを取る値オブジェクト。

| 値 | 意味 |
|---|---|
| `Owner` | 作成者。プロジェクトごとに必ず1人、変更・削除不可 |
| `Admin` | 管理者権限（メンバー管理が可能） |
| `Member` | 一般メンバー |

### 3.3 Board / Column

- `Board`: プロジェクトに1つ紐づく（`ProjectId`, `Name`, `Columns`）。
- `Column`: ボードに属する列（`BoardId`, `Name`, `Order`, `Tasks`）。ステータスを表す固定列挙は存在せず、自由に作成・命名可能な構造。既定のボード作成フロー（Web UI）では `ToDo` / `進行中` / `完了` の3列を自動生成する。

### 3.4 BoardTask（タスク）

| フィールド | 型 | 説明 |
|---|---|---|
| `Id` | Guid | 主キー |
| `ColumnId` | Guid | 所属する列 |
| `Title` | string | タイトル（必須、500文字以内） |
| `Description` | string | 説明（2000文字以内） |
| `AssigneeId` | Guid? | 担当者（未割り当て可） |
| `CreatorId` | Guid | 作成者 |
| `Order` | int | 列内の並び順 |
| `DueDate` | DateTime? | 期限（任意） |
| `Priority` | Priority | 優先度（既定値 `Medium`） |
| `CreatedAt` / `UpdatedAt` | DateTime | 作成・更新日時 |
| `Comments` | TaskComment[] | コメント一覧 |

- `Update(title, description, assigneeId, dueDate, priority)`: `AssigneeId` が**変更されて**新たに非nullになった場合のみ `TaskAssignedEvent` を発行する（作成時に初期担当者を指定しても通知は発火しない — 編集による割り当て変更時のみ）。
- `Move(newColumnId, newOrder)`: 列間移動・並び替え。
- `AddComment(authorId, body)`: `TaskCommentedEvent` を発行。

### 3.5 Priority（優先度）

| 値 | 画面表示 |
|---|---|
| `Low` | 低 |
| `Medium`（既定値） | 中 |
| `High` | 高 |
| `Critical` | 緊急 |

> 補足: リポジトリ内には `TaskFlow.Domain/Tasks/` 配下に、上記とは別の未使用のレガシードメインモデル（`TaskItem`, `TaskItemStatus` 等）が残存しているが、WebAPI・Application層のいずれからも参照されていない死コードであり、現行の仕様には含まれない。

### 3.6 TaskComment（コメント）

| フィールド | 説明 |
|---|---|
| `Id` / `TaskId` / `AuthorId` / `Body`（必須、2000文字以内） / `CreatedAt` | `BoardTask.AddComment` 経由でのみ生成される |

### 3.7 Notification / NotificationType

| フィールド | 説明 |
|---|---|
| `UserId` | 通知の宛先 |
| `Message` | 日本語メッセージ |
| `Type` | 下表参照 |
| `RelatedEntityId` | タスクIDまたはプロジェクトID |
| `IsRead` | 既読フラグ（既定 false） |

`NotificationType` は次の3値のみ： `TaskAssigned` / `TaskCommented` / `MemberInvited`（詳細は7章）。

## 4. 権限モデル

ロールはプロジェクト単位（`ProjectMember.Role`）。

| 操作 | Owner | Admin | Member |
|---|:---:|:---:|:---:|
| プロジェクト閲覧・ボード/タスクの閲覧・作成・編集・移動 | ○ | ○ | ○ |
| コメント投稿 | ○ | ○ | ○ |
| メンバー招待・ロール変更・削除 | ○ | ○ | ✕ |
| プロジェクト削除 | ○ | ✕ | ✕ |
| プロジェクト名/説明の編集 | ○ | ○ | ○（※） |

> ※ 現行実装では `UpdateProjectCommand` はメンバーであることのみを確認しており、ロールによる制限がかかっていない。仕様上の制約というより実装上の既知の挙動として記載する。

その他の個別制約：
- コメント削除: 投稿者本人のみ（ロール不問）
- 通知の既読化: 通知の受信者本人のみ
- タスク削除・列/ボードのCRUD: プロジェクトメンバーであれば誰でも可（ロール制限なし）
- 非メンバーがアクセスした場合は `ForbiddenAccessException` → HTTP 403

## 5. API仕様

すべて `/api` 配下、特記なき限り JWT Bearer 認証必須。

### 5.1 認証系（`AuthEndpoints.cs`）

| Method | Route | 認証 | 概要 |
|---|---|:---:|---|
| POST | `/api/auth/register` | 不要 | アカウント登録（Email, Password, DisplayName） |
| POST | `/api/auth/login` | 不要 | ログイン（Email, Password） |
| GET | `/api/auth/me` | 必須 | ログイン中ユーザーのプロフィール取得 |

### 5.2 プロジェクト系（`ProjectEndpoints.cs`）

| Method | Route | 権限 | 概要 |
|---|---|---|---|
| GET | `/api/projects` | メンバー | 所属プロジェクト一覧 |
| GET | `/api/projects/{id}` | メンバー | プロジェクト詳細 |
| POST | `/api/projects` | 任意ユーザー | プロジェクト作成（作成者がOwnerになる） |
| PUT | `/api/projects/{id}` | メンバー | 名称・説明の更新 |
| DELETE | `/api/projects/{id}` | Owner | プロジェクト削除 |
| GET | `/api/projects/{id}/members` | メンバー | メンバー一覧 |
| POST | `/api/projects/{id}/members` | Owner/Admin | メンバー招待（Role は `Admin`/`Member` のみ指定可） |
| PUT | `/api/projects/{id}/members/{uid}` | Owner/Admin | メンバーのロール変更 |
| DELETE | `/api/projects/{id}/members/{uid}` | Owner/Admin | メンバー削除 |

### 5.3 ボード / 列 / タスク / コメント系（`BoardEndpoints.cs`）

| Method | Route | 概要 |
|---|---|---|
| GET | `/api/projects/{id}/board` | ボード取得（列・タスクを順序付きで含む） |
| POST | `/api/projects/{id}/boards` | ボード作成 |
| POST | `/api/boards/{id}/columns` | 列の作成 |
| PUT | `/api/columns/{id}` | 列名の変更 |
| POST | `/api/columns/{id}/tasks` | タスク作成（Title, Description, AssigneeId?） |
| GET | `/api/tasks/mine` | 自分が担当する全プロジェクト横断のタスク一覧 |
| GET | `/api/tasks/{id}` | タスク詳細 |
| PUT | `/api/tasks/{id}` | タスク更新（Title, Description, AssigneeId?, DueDate?, Priority） |
| PUT | `/api/tasks/{id}/move` | タスク移動（TargetColumnId, NewOrder）。SignalRで `TaskMoved` をブロードキャスト |
| DELETE | `/api/tasks/{id}` | タスク削除 |
| GET | `/api/tasks/{id}/comments` | コメント一覧 |
| POST | `/api/tasks/{id}/comments` | コメント投稿 |
| DELETE | `/api/comments/{id}` | コメント削除（投稿者本人のみ） |

### 5.4 通知系（`NotificationEndpoints.cs`）

| Method | Route | 概要 |
|---|---|---|
| GET | `/api/notifications` | 自分宛の通知一覧 |
| PUT | `/api/notifications/{id}/read` | 1件を既読化 |
| PUT | `/api/notifications/read-all` | 全件既読化 |

## 6. リアルタイム通信仕様（SignalR）

| Hub | パス | クライアントメソッド | サーバーからの配信 |
|---|---|---|---|
| `BoardHub` | `/hubs/board` | `JoinBoard(boardId)` / `LeaveBoard(boardId)` | タスク移動時に `TaskMoved`（Id, ColumnId, Title, Description, AssigneeId, Order）をボード閲覧者全員へ配信 |
| `NotificationHub` | `/hubs/notification` | `JoinUserGroup(userId)` / `LeaveUserGroup(userId)` | 新規通知作成時に `UnreadCountUpdated(count)` を該当ユーザーへ配信 |

Web UIは自動再接続（`WithAutomaticReconnect()`）に対応。

> **既知の課題**: 両Hubとも `[Authorize]` が付与されておらず、JWT認証なしで誰でも接続・グループ参加できる状態（REST APIとは異なりHub単位での認可が未実装）。boardId/userIdを知っていれば第三者がタスク移動やユーザーの未読件数更新を購読できてしまうため、本番運用前にはHubの認証・認可対応が必要。

## 7. 通知トリガー仕様

| NotificationType | 発火条件 | 宛先 | メッセージ |
|---|---|---|---|
| `TaskAssigned` | タスク編集で `AssigneeId` が新たに設定/変更された時（作成時の初期担当者指定では発火しない） | 新しい担当者 | 「タスクがアサインされました」 |
| `TaskCommented` | コメント投稿時 | タスクの現担当者（いれば）とタスク作成者（いずれもコメント投稿者本人を除く、重複排除） | 「タスクにコメントが追加されました」 |
| `MemberInvited` | メンバー招待時 | 招待されたユーザー | 「プロジェクトに招待されました」 |

## 8. バリデーション仕様一覧

| 対象 | ルール |
|---|---|
| プロジェクト名 | 必須、200文字以内 |
| プロジェクト説明 | 必須、1000文字以内 |
| ボード/列名 | 必須、200文字以内 |
| タスクタイトル | 必須、500文字以内 |
| タスク説明 | 2000文字以内 |
| コメント本文 | 必須、2000文字以内 |
| 表示名（DisplayName） | 1〜50文字 |
| メールアドレス | 有効な形式であること |
| パスワード | 8〜100文字 |
| 招待/ロール変更時のRole | `"Admin"` または `"Member"` のみ（`"Owner"` 指定は不可） |

## 9. 認証・トークン仕様

- JWT Bearer認証（HMAC-SHA256、`TaskFlow.Infrastructure/Auth/JwtTokenService`）
- 有効期限: 既定60分（`appsettings.json` の `JwtSettings:ExpiryMinutes`）
- Issuer: `TaskFlow.WebAPI` / Audience: `TaskFlow.Clients`
- クレーム: `sub`（ユーザーID）、`email`、`name`、`jti`（`MapInboundClaims=false` によりクレーム名をそのまま保持）
- クライアント側ではトークンをブラウザの `localStorage`（キー: `authToken`）に保存し、各リクエストに `Authorization: Bearer <token>` ヘッダーとして付与

## 10. 運用機能: エラー自動解析パイプライン

エンドユーザー向け機能ではないが、運用上の特徴として記載する。

API側で未処理の500系例外が発生すると、レスポンスをブロックしない非同期パイプラインが起動し、以下を行う：

1. Claude API（`ClaudeExceptionAnalyzer`）による原因・影響範囲・修正方針の自動解析
2. 解析結果と例外情報を Markdown形式で `logs/errors/{日付}/` 配下に保存（AIエージェントが読み込んで修正提案を行える構造化フォーマット）
3. （SMTP設定済みの場合）担当者へのメール通知

`appsettings.json` の `ErrorAnalysis` セクションで有効/無効・APIキー・SMTP設定を管理し、開発環境では既定で無効化されている。

## 11. 既知の制約・現行UIの範囲

以下はAPIとしては実装されているが、Web UI（Blazor）からは操作できず、Swagger/OpenAPI（開発環境: `/openapi`）等での直接API呼び出しが必要：

- メンバーの招待・ロール変更・削除
- プロジェクトの編集・削除
- 列（Column）の追加・ボードの追加作成
- タスクの新規作成・削除
- コメントの削除

Web UIから現在利用できる機能の詳細は「利用説明書.md」を参照。
